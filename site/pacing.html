Pacing

How Ordeal paces calls

Each model has its own limit on how many requests and how many tokens it accepts per minute. Ordeal waits inside those limits, so a batch run is paced to each model rather than to one fixed number of calls.

Two limits per model

A model can refuse calls for two reasons. It limits the number of requests in a minute, and it limits the number of tokens in a minute. A token is a small piece of text, so a long question uses more of the token limit than a short one. The two numbers differ a lot from model to model, so one fixed number of calls at once suits none of them.

Where the numbers come from

Ordeal first reads the limits from the rate-limit headers sent with each reply from an endpoint. The provider can change them, and the newest reply shows the current limit. Until a reply has come back, Ordeal uses the console table copied from the provider's page. A model in neither gets a low default, so an unknown model starts slowly.

How a call waits

Before a call is sent, Ordeal checks the room left in both limits for that model. Each limit refills as the minute goes by. A call waits until both have room for it. Ordeal uses only 85% of each limit, so a burst of retries does not reach the provider's real ceiling. If the provider sends a scale factor, meaning it has cut the limit for now, that factor is applied as well.

How many calls run at once

The number of calls in flight at once is the requests per second times the measured reply time, with a margin of one and a half. A fast model can therefore take more calls at once than a slow one with the same limit. The count is kept between 2 and 64.

When a provider refuses a call

A refusal with status 429 means the provider has said there are too many calls. Ordeal pauses only that model for the time the provider asks for. The other models keep running.
